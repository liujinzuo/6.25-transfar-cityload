## 三、发现的问题（4 项，均已修复并复验）

### BUG-1 · 数据目录缺文件时抛裸异常　`严重度：中`

**复现**

```bash
python -m cityload.cli benchmark --data path/to/empty_dir --out out
```

**现象**：输出 `FileNotFoundError` 的完整 Python 堆栈，无任何业务提示。

```
File "cityload/dataio.py", line 87, in _rows
    with open(path, newline="", encoding="utf-8-sig") as fh:
FileNotFoundError: [Errno 2] No such file or directory: '...\emptydir\stores.csv'
```

缺任意一个 CSV（如只缺 `vehicles.csv`）同样如此。

**影响**：评审用真实数据替换时路径写错或目录不完整，看到的是堆栈而非「你缺了哪个文件」。

**修复**：`dataio` 新增 `DataFormatError`，载入前显式校验四个必需文件；`cli` 统一捕获并给出可照做的提示；退出码规范为 `3`。

**复验**

```
[✗] 数据目录 ...\emptydir 缺少必需文件：stores.csv, skus.csv, order_lines.csv, vehicles.csv
    该目录需要这四个 CSV：stores.csv, skus.csv, order_lines.csv, vehicles.csv
    表头格式见 data/README.md；也可先跑 `python -m cityload.cli data` 生成一份样例照着改。
EXIT=3 ✔
```

### BUG-2 · 配置文件带 UTF-8 BOM 直接崩溃　`严重度：高`

**复现**：把 `configs/default.json` 用**记事本另存为 UTF-8**（或 PowerShell `Set-Content -Encoding UTF8`、Excel 导出），再运行：

```
json.decoder.JSONDecodeError: Unexpected UTF-8 BOM (decode using utf-8-sig): line 1 column 1 (char 0)
```

**影响**：这是**评审在 Windows 上手改配置的最常见路径**——改个门店数或成本参数就会踩到。不夸张地说，这一条足以让评审认为「项目跑不起来」。

**根因**：`pipeline.load_config` 用 `encoding="utf-8"` 打开；而同一个仓库的 `dataio._rows` 读 CSV 时用的却是 `utf-8-sig` —— **前后不一致**，属于疏漏而非设计。

**修复**：`load_config` 改用 `utf-8-sig`（透明剥离 BOM）；同时把 JSON 语法错误包装成 `ConfigError` 给出中文提示；退出码规范为 `2`。

**复验**

```
带 BOM 的配置文件 → EXIT=0 ✔
{ "seed": 1, }   → [✗] 配置文件 ... 不是合法 JSON：Expecting property name ...
                    常见原因：多余逗号、中文引号、注释。可对照 configs/default.json 检查。
                   EXIT=2 ✔
```

## 四、附带发现（未修改，供后续决策）

### OBS-1 · 命令必须在仓库根目录执行

从其它目录运行 `python -m cityload.cli` 会得到标准 Python 报错 `No module named 'cityload'`（这是 Python 的正常行为，不是缺陷），但 README 原先没写明这个前提。

**处理**：已在 README「快速开始」补一句运行前提说明；设好 `PYTHONPATH` 后从任意目录运行均可（实测退出码 0）。

### OBS-2 · `.gitignore` 与实际入库内容自相矛盾

`.gitignore` 声明忽略 `data/synthetic/`，但由于本次是用 GitHub API 推送（不经过 git，自然也不读 `.gitignore`），该目录**实际已在仓库里**。评审若 clone 后运行 `cli data` 再 `git status`，会看到这些「本应被忽略」的文件变成 modified。

**处理**：已改为**显式不忽略**并在 `.gitignore` 中写明原因 —— 随仓库提供样例数据，便于评审不跑代码也能直接查看 CSV 结构与字段。

### OBS-3 · 提交表单里的描述文字已略微过期

问卷星表单第 5 题填的是「39 个单元测试全绿」，而仓库现为 45 个。表单已提交、无法修改，**不影响评审**（仓库内为准，且 45 > 39 只会更好）。

## 六、本次黑盒测试暴露的方法论问题

4 个问题里有 **3 个与「主流程」无关**，全部出在**边界输入**与**文档准确性**上：

1. **只测 happy path 会漏掉大部分真实风险**。主流程我第一次就通过了，但评审真正会踩的是「路径写错」「记事本改配置」这类动作。
2. **文档里的数字必须由实际运行产生，不能凭印象写**。本次 5 处耗时、1 处测试数都是凭写文档时的记忆填的，全部失真。
3. **同一个仓库里相同的事情要用同一种做法**。CSV 读了 BOM、JSON 没读，这种不一致几乎必然是疏漏点。

这也是为什么黑盒测试应该在提交**之前**做 —— 本次是在提交之后补做的，
好在仓库链接是长期入口，修复后重新推送即可生效。
