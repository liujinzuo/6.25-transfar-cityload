# 06 · 当前限制与落地路径

本文件按赛题《作品提交与评审说明》的要求，**区分已验证效果与预期收益**，
把方案现阶段的限制、已定位的成因与改进路线逐条写清。

---

## 1. 已定位的核心限制：一维功能区分配与装载率存在结构性张力

### 现象

启用严格功能区隔离后，装载器会在**车厢只用了约 24%** 的情况下报出未装载箱垛
（典型算例：213 个整箱垛中 45 个装不下，最大码放高度只到车厢可用高度的 55%）。
不启用功能区隔离时，同样一车货 0 未装载。

### 已定位的成因

1. **功能区长度按体积分配，但车厢长度是「地板」资源。**
   体积占比等价于地板占比的前提是货物能码到车厢顶。实测本装载器对异构箱垛
   平均只叠到约 1.4 层，于是地板面积成为紧约束，按体积切分会让**每个功能区都缺地**。
2. **细粒度切分（切到「门店 × 功能区」）会彻底失效。**
   细条宽 150–400mm，一个门店在一个功能区里的货只能叠成一根高塔，
   顶到天花板后剩余货物向全车逃逸，功能区边界形同虚设。
   （实测：容积利用率 27.8% → 23.6%，未装载 0 → 45。）
3. **极值点候选集只从已放置箱体的角点生长，空区域没有候选点。**
   这会放大前两个问题（已通过铺地板网格部分缓解）。

### 已经做出的应对

- 功能区长度改为**按底面面积（footprint）分配**，直接对齐紧约束；
- 功能区内**不再切细条**，改为逐店顺序码放；
- 空间分配进入**闭环回检**（试装 → 按未装载情况重新分配 → 再试装）；
- 引入**三级降级**（严格分区 → 分区作偏好 → 全区集中码放），
  并把降级比例作为指标 `relaxed_loads` / `unallocated_loads` / `zone_violations` 暴露，
  **不把代价藏起来**。

### 仍然存在的缺口（诚实结论）

在当前装载器下，**严格功能区隔离与高装载率尚未同时达成**。
从最终对照实验可以看到：启用空间分配的方案（B、D）在多数车次上会降级到
「未做空间分配」，因此 **B 与 A 的指标接近、D 与 C 的指标接近** ——
空间分配的设计收益**没有在当前装载器下兑现**。
这正是本方案最需要继续投入的方向。

## 2. 具体的改进路线（按预期收益排序）

| # | 改进项 | 预期收益 | 工作量 |
|---|--------|---------|--------|
| 1 | **二维功能区布局**：功能区不再只沿车长切分，而是同时沿车宽切分（例如日化占一侧、药品占另一侧、冷链贴门），使每个功能区都能用满车长 | 直接消除「窄条高塔」问题，是本方案最关键的一步 | 中 |
| 2 | **按楼层分配**：为每个功能区分配「地板层 + 允许的层数」，而不是只分配长度；层内再用 2D 装箱 | 让分配与「能叠几层」这一真实约束对齐 | 中 |
| 3 | **候选点集补全**：在空区域按箱垛尺寸自适应播种候选点（而不是固定网格），并补充投影点 | 提升可放位置覆盖率，减少「有地方放不进去」 | 小 |
| 4 | **装载器与排线的联合标定**：`planning_volume_derate` 目前是常数，应改为随货物规格分布自动标定 | 消除排线与配载之间的接口误差 | 小 |
| 5 | **引入成熟 3D 装箱求解器**做对照（如 OR-Tools CP-SAT 建模） | 给出「本装载器离最优还有多远」的量化上界 | 中 |
| 6 | **路径级可行性与配载的联合优化**：目前路径批量搜索与配载是串行的两层循环，可合并为一次搜索 | 降低求解时间 | 中 |

## 3. 建模简化（已知与真实业务的差距）

| 简化项 | 当前做法 | 真实业务 | 影响 |
|--------|---------|---------|------|
| 路网 | 直线距离 × 1.25 绕行系数 | 真实路网距离矩阵 + 分时段通行速度 | 里程与时效为近似值 |
| 装载方向 | 只允许水平面内 90° 旋转，不允许侧放/倒置 | 部分货物可侧放，部分必须保持直立 | 装载率偏保守 |
| 承重 | 单箱可承压上限按**直接支撑**分摊 | 真实承压是整柱累加，且与垛型稳定相关 | 可能高估可叠层数 |
| 卸货通道 | 假设尾门单侧卸货，用 x 顺序刻画 | 实际可能有侧门、叉车通道 | 装卸指引需按现场调整 |
| 时间窗 | 硬约束，早到等待 | 部分门店允许弹性窗口 | 路径数可能偏多 |
| 成本 | 固定成本 + 里程成本 | 还含人工工时、装卸费、超时罚金 | 成本口径需业务方替换 |
| 数据 | 全部为合成数据 | 真实 SKU 尺寸、订单分布 | 结论的相对关系可参考，绝对值不可外推 |

## 4. 工程化落地路径

从当前原型走向生产系统，建议分四步：

**第 1 步 · 数据对接（1–2 周）**
- 接入 WMS/TMS 的 SKU 主数据（尺寸、重量、耐压、温层）
- 接入订单数据（门店、SKU、数量、时间窗）
- 接入运力数据（车型、车厢内尺寸、载重、成本）
- 用 `cityload.dataio.load_instance` 替换合成数据，跑通同一套算法

**第 2 步 · 规则校准（2–3 周）**
- 由业务方核对 `categories.py` 的品类-功能区映射与禁压/不相容规则
- 实测标定 `planning_volume_derate`（装载器可达效率）
- 用历史车次回放校准成本口径与车速

**第 3 步 · 装载器增强（3–6 周）**
- 落地上文改进路线 1–3（二维布局、楼层分配、候选点补全）
- 引入 CP-SAT 对照，量化与最优解的差距

**第 4 步 · 现场闭环（持续）**
- `reports/loadplan.html` 接入车载终端/手持终端，替代纸质装车单
- 采集实际装车结果（装载率、倒腾次数、超时率）回流校准

### 进入企业环境需要明确的条件

| 约束 | 说明 |
|------|------|
| 数据安全 | 接入真实订单与客户信息需满足赛事方的数据使用与保密要求；建议先在脱敏数据集上验证 |
| 系统对接 | 需要 WMS（SKU 主数据、库存）、TMS（订单、运力）、车载终端三个接口 |
| 部署成本 | 本方案为零第三方依赖的纯 Python 实现，可单机部署；全流程约 3 分钟/算例（实测 185 s），日配送计划一次生成即可 |
| 运维成本 | 主要成本在**规则表维护**（品类增加、法规变化），算法本身几乎不需要运维 |
| 关键障碍 | 品类合规规则往往分散在老师傅经验里，需要一轮系统性的知识抽取 |

## 5. 诚实的收益表述

| 已经过本仓库实验验证 | 属于预期收益（尚未验证） |
|---------------------|------------------------|
| 节约算法 + 2-opt 相对最近邻贪心可缩短总里程（见 `docs/05`） | 二维功能区布局能同时拿到高装载率与品类隔离 |
| 交付顺序对齐可显著降低重复搬运段数（在空间充足时） | 接入真实数据后成本降幅能达到实验室水平 |
| 配载感知的车型指派能避免「体积够但形状装不下」的错配 | 现场装卸时间能按倒腾指数等比例下降 |
| 空间分配与高装载率在当前装载器下存在结构性张力（本仓库已量化） | 引入 CP-SAT 后装载率能追上商业求解器 |
